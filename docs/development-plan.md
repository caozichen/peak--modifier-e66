# 当前环境准备与后续开发计划

当前基线：桌面 0.3.2、插件 0.2.6。历史原始计划在 [archive/original-development-plan.md](archive/original-development-plan.md)，其中工具选择与旧版本限制不作为当前要求。

## 阶段 1：环境和材料

- 运行测试者：Windows x64、Steam PEAK、可写便携目录即可；运行自包含版无需安装 SDK。
- 构建者/AI：.NET SDK 10.0.403、PowerShell、Git；按 README 准备官方 BepInEx x64 Mono 和本机 Managed 引用。
- 确认 `dotnet --version`；记录 Steam Build、程序集 SHA256、本插件版本；这些信息用于排查差异，不构成游戏版本封锁。
- 游戏 DLL、编译产物及依赖缓存保留在本机；源码仓库保存获取方式、固定版本、哈希、引用路径与脚本。

## 阶段 2：理解当前代码

先读 `Shared/FeatureCatalog.cs`、`WireMessage.cs` 和架构说明，再依次检查界面、PipeClient/Server、TrainerPlugin、GameAdapter 及各功能 partial。新增功能必须明确作用对象、房主要求、可撤销状态和缺失接口时的提示。

保留以下行为约束：新窗口默认关闭；同一游戏进程内的场景往返不清空选择；暂不可用时只暂停效果；一次性操作不重放；手动恢复/停用明确清空；只撤销自身补丁。

## 阶段 3：实现功能改动

1. 在 FeatureCatalog 定义稳定 ID、易懂名称、默认值、范围、说明；两端共用目录。
2. 实现实际游戏接口检查与能力报告；只对当前本地角色或已验证拥有的对象生效。
3. 调整参数时验证完整快照、边界和非有限数值；复杂 IL 匹配不得靠猜测插入。
4. 临时写入对象/材质必须记录恢复条件，限制缓存，处理场景与对象销毁。
5. 更新功能说明、名称映射及对应的有意义回归，避免仅复制实现的断言。

## 阶段 4：离线验证

运行 Build 与 Test；必要时执行实际程序集只读 IL 分析。查看报告，而不是只看编译成功。检查原有功能、通信超时/重连、旧请求取消、跨场景保留、停用、安装回滚、路径和文件所有权。

## 阶段 5：由用户运行游戏验证

按 testing.md 矩阵分组测试：机场识别、单项倍率、状态清除、机场往返、死亡复活、权限变化、断线重连、手动恢复与停用。长时间运行要观察进程内存/句柄、异常日志增长、场景循环后对象缓存；短时间替身检查不能证明不存在所有泄漏。

## 阶段 6：生成测试目录与交付

插件改动后先重新 Build，以同步内嵌插件哈希，再验证并 Publish。优先生成本地目录供测试，明确需要分享时才加 `-Zip`。发布目录必须是新目录；不复制个人设置、日志、备份及安装记录。发布前校验文件清单和第三方许可说明。

涉及安装或替换游戏文件时先关闭游戏和旧窗口，保留可恢复备份。源码更新和构建不需要停止正在运行的游戏，也不会自动部署。
